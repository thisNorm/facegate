# 03. 시스템 아키텍처 설계서

버전 0.1 · 2026-10-27

## 1. 먼저 알아야 할 제약: 기존 AI 서버의 동작 방식

기존 얼굴인식 AI 서버(기존 엣지 서버의 얼굴인식 API 연동 문서)는 **"사진을 보내면 결과를 돌려주는" 방식이 아닙니다.** AI 서버가 주도권을 가집니다.

1. AI 서버가 엣지서버에서 **카메라 RTSP 주소**와 **등록 얼굴 사진**을 받아감
2. AI 서버가 RTSP 영상을 직접 읽으며 계속 분석
3. 사람이 나타나면 엣지서버로 `appear`(누구인지, 사진 포함), 사라지면 `disappear`를 보냄

따라서 **안드로이드 단말이 사진을 찍어 AI로 보내는 구조는 지금 AI 서버로는 안 됩니다.** 아래 세 가지 구성안 중 하나를 골라야 합니다 (Q-01).

## 2. 구성안 비교

| | 안 A: 게이트별 IP 카메라 (권장) | 안 B: 안드로이드 카메라를 RTSP로 송출 | 안 C: AI 서버에 동기식 API 추가 |
|---|---|---|---|
| 얼굴 촬영 | 게이트에 붙인 소형 IP 카메라 | 안드로이드 단말 카메라 | 안드로이드 단말 카메라 |
| AI 서버 수정 | **없음** (주소·키만 변경) | 없음 | **새 API 개발 필요** |
| 안드로이드 앱 역할 | 화면 표시 | 화면 + RTSP 송출 | 화면 + 촬영·전송 |
| 장점 | 기존 방식 그대로, 가장 안정적, 단말이 죽어도 인식은 계속 | 카메라 추가 구매 없음 | 응답 시간 통제 쉬움, 업계 단말과 같은 구조 |
| 단점 | 카메라·배선 추가 | 안드로이드 RTSP 송출은 발열·끊김 위험, 앱 복잡 | AI 서버 담당과 협의·개발 필요 |

**결정: 안 B (D-06, D-56에서 확정). 단말 = 카메라가 달린 안드로이드 기기 하나이며, 시스템 전체에서 별도 카메라 개념을 두지 않는다. 단말 번호가 AI의 `device_key`다.** AI 서버 수정 없이, 카메라를 따로 사지 않고, 화면과 카메라가 한 몸이라 사람이 자연스럽게 화면을 봅니다. 대신 안드로이드 단말의 24시간 영상 송출 안정성이 가장 큰 위험이므로 **1단계에서 PoC로 먼저 검증**하고, 실패하면 안 A로 전환합니다 (8장).

안 A로 바꾸더라도 게이트 서버·웹 관리자·단말 화면은 그대로 쓰고, 단말 앱에서 송출 기능만 빠집니다. 그래서 송출 기능은 앱 안에서 **따로 떼어낼 수 있는 모듈**로 만듭니다.

## 3. 전체 구성도 (안 B 기준)

```
 ┌────────────────────────────── 사내망 / Tailscale ──────────────────────────────┐
 │                                                                                │
 │  [안드로이드 단말] ① 카메라 영상 송출 (RTSP 서버 내장)                              │
 │       │   ▲                                                                    │
 │       │   └─ ⑤ 판정 결과 (WebSocket) ─────────────────────┐                     │
 │       ▼                                                   │                     │
 │  [얼굴인식 AI 서버] ── ② appear/disappear ──▶ [게이트 서버] ──③ 릴레이 명령──▶ [릴레이 모듈] ──④ 드라이 접점──▶ [스피드게이트]
 │   (기존, 수정 없음)  ◀── RTSP 목록·얼굴 데이터셋 ──┘   │                           │
 │                                                   ├──▶ [웹 관리자] (PC 브라우저) │
 │                                                   └──▶ [원격 관리 서버] (Heartbeat)
 └────────────────────────────────────────────────────────────────────────────────┘
```

- ① 단말이 전면 카메라 영상을 RTSP로 내보내고, 게이트 서버가 AI에 주는 RTSP 목록(`GET /rtsp`)에 **단말 주소**를 넣습니다.
- ② AI는 기존 CCTV와 똑같이 그 영상을 분석해 `appear`를 보냅니다.
- ③④ 게이트 서버가 허가를 판단하고 릴레이로 게이트를 엽니다. **열림 신호는 단말이 아니라 서버에서** 나갑니다.
- ⑤ 판정 결과는 단말 화면에 표시합니다.
- **NFC (D-12):** 얼굴이 안 될 때 사진 사원증 뒷면의 NTAG 424 DNA 스티커를 단말에 대면, 단말이 스티커의 암호값(SUN)을 WebSocket으로 서버에 보내고, 서버가 검증한 뒤 ③④와 같은 방식으로 엽니다. NFC는 AI 서버를 거치지 않으므로 **AI 서버가 멈춰도 출입 가능**합니다.

## 4. 출입 흐름과 응답 시간

| 순서 | 동작 | 예상 시간 | 확인 |
|---|---|---|---|
| 1 | 직원이 단말 카메라 범위 진입 | — | |
| 1-1 | 단말 인코딩 → RTSP → AI 서버 수신 | 100~300ms (RTSP 버퍼) | PoC 실측 |
| 2 | AI 확정(같은 사람 N회 일치) 후 `appear` 전송 | **현재 최악 약 3초** (초당 4장×4회 ≈1초 + 폴더 확인 2초) → 게이트 설정 목표 **0.5초 이내** | 09 문서 AI-01·02 |
| 3 | 게이트 서버: 직원·권한 조회, 중복 개방 체크 | < 20ms | |
| 4 | 릴레이 펄스 (0.3~0.5초) → 게이트 열림 | 50~100ms + 게이트 구동 | |
| 5 | 동시에 단말에 결과 전송 (WebSocket) | < 50ms | |
| 6 | 통과 후 게이트 자동 닫힘 | 게이트 담당 | Q-04 |

**가장 큰 위험은 2번입니다.** 코드 확인 결과(09 문서), 처음에 미등록으로 판정돼도 이후 직원으로 인식되면 직원 appear가 다시 나갑니다. 대신 지금 설정으로는 최악 약 3초가 걸리므로 AI 프로그램을 게이트용으로 바꿔야 합니다 (AI-01~04).

- 게이트 서버는 **사진 저장을 판정 뒤로 미룹니다**(응답 먼저, 저장은 비동기).
- `disappear`는 기록 보완용이며 개방 판단에 쓰지 않습니다.

## 6. 장애 대응

| 상황 | 동작 |
|---|---|
| AI 서버 다운 | 얼굴 인식 불가 → 단말 "점검 중" 표시, **NFC로 출입 계속**, 대시보드 경보 |
| 게이트 서버 다운 | 얼굴·NFC 모두 개방 불가 → 게이트는 닫힌 상태 유지(보안 우선). 게이트 수동 개방·보안요원 |
| 송출만 끊김 | 얼굴 인식 불가, **NFC는 동작**. AI `status`의 `rtsp_ok:false` → 대시보드 경보. 앱 자체 감시(watchdog)로 송출 재시작 |
| 단말 앱 다운 | 얼굴·NFC 모두 불가 (안 B의 약점). watchdog으로 앱 재시작, 실패 시 게이트 수동 개방 |
| 단말 기기 다운 | 하드웨어 watchdog·자동 부팅(산업용 단말 기능)으로 복구. 복구 전까지 대체 수단 |
| 릴레이 모듈 통신 실패 | 판정은 기록, 단말에 "게이트 오류" 표시, 경보 |
| 정전·화재 | 게이트 자체 fail-safe와 화재수신반 연동으로 개방 (소프트웨어 무관) |

## 7. 보안

- 열림 신호는 서버 → 릴레이 모듈로만 나갑니다. 단말에는 게이트를 직접 여는 기능이 없습니다.
- 릴레이 모듈은 게이트 서버만 접근 가능한 망에 둡니다 (VLAN 또는 방화벽).
- AI 수신 API: 기존과 같은 `X-Ingest-Key`. 단말: 단말별 토큰. 관리자: 로그인 세션.
- 얼굴 사진은 서버 디스크에 저장하고 외부 전송하지 않습니다 (AI 서버로만 제공).
- NFC: 단말은 스티커 값을 읽어 보내기만 하고 **검증·판정은 서버**가 합니다. 단말 토큰이 없는 기기가 보낸 값은 거부합니다.
  - 스티커 UID는 누구나 읽고 흉내 낼 수 있으므로 **UID만으로는 절대 통과시키지 않습니다.** 태그할 때마다 바뀌는 SUN 값(암호화된 UID·카운터 + CMAC)을 검증하고, 카운터가 이전보다 커야만 통과 (복사·재전송 방지).
  - 키 구조: 서버의 마스터 키(AES-128) + 스티커 UID → 스티커별 키 파생. 스티커 하나가 털려도 다른 스티커에 영향 없음.
  - 발급 때 필요한 암호 계산도 서버가 하고 단말은 명령만 중계 → **단말을 훔쳐도 키가 없음.**
  - 마스터 키를 잃으면 모든 스티커를 다시 발급해야 하므로 오프라인 백업 (NFR-16).
- 단말 RTSP 스트림은 계정·비밀번호를 걸고(RTSP 인증), AI 서버 IP에서만 접속 허용합니다. 로비 단말 영상이 사내망에 열려 있으면 누구나 볼 수 있기 때문입니다.

## 8. 안 B 위험과 PoC 기준

안 B는 "안드로이드 앱이 CCTV 역할까지 한다"는 점이 핵심 위험입니다. 1단계에서 아래를 먼저 시험합니다.

| 위험 | 대응 | PoC 통과 기준 |
|---|---|---|
| 24시간 송출 시 발열·앱 종료 | 하드웨어 인코딩, 1080p·15fps (송출 확인됨), 산업용 단말 | **72시간 연속 송출, 끊김 자동 복구 100%**, 본체 온도 안정 |
| 송출 지연으로 응답 느림 | 낮은 GOP(1초), RTSP 버퍼 최소화 | 얼굴 진입 → `appear` 수신 **0.8초 이내** |
| 화면 표시와 카메라 동시 사용 | CameraX 미리보기 + 인코더 동시 출력 | 미리보기 끊김 없음 |
| 화질 (역광 로비) | 노출 고정·얼굴 영역 노출 보정 | 직원 10명 × 20회 본인 인식률 97% 이상 |
| AI 서버 RTSP 재접속 | 단말 재부팅 후 같은 주소 유지(고정 IP) | AI가 수동 조치 없이 재연결 |
| 위조 얼굴 (D-25) | 등록 직원의 휴대폰 사진·휴대폰 영상·출력 사진을 단말 앞에 각 20회 | **한 번이라도 열리면 위조 방지 모델 추가** (AI-05) |

(D-56으로 안 B 확정. 아래는 처음 계획한 전환 기준이며 기록으로 남김) **위조 얼굴을 뺀 나머지 항목 중 하나라도 통과 못 하면 안 A로 전환**합니다 (위조 얼굴은 카메라 방식과 무관하므로 AI 쪽에서 해결). 그때 바뀌는 것은 IP 카메라 구매와 단말 앱의 송출 모듈 제거뿐입니다.


## 9. 단말 기기 선정 체크리스트 (D-18)

후보: **WA8059T (RK3576S)** 벽부형 안드로이드 태블릿. RK3576은 H.264 하드웨어 인코더(4K급)와 6 TOPS NPU가 있어 안 B의 24시간 송출에 여유가 있습니다. ("S" 버전의 차이는 공개 자료로 확인하지 못함 → 판매처에 확인)

| 항목 | 조건 | 왜 필요한가 |
|---|---|---|
| 전원·네트워크 | **PoE (IEEE 802.3at)** + 유선 LAN, 배터리 없음 | 24시간 상시 동작, 배터리 팽창 방지, 배선 1가닥 |

| 방열 | 팬리스 금속 후면 등 방열 구조, 24시간 동작 보증 | 송출 발열 |

| 화각, 센서 모델, 최대 촬영 FPS, WDR | 미확인 |
| NFC | **Android 표준 NFC 확인** (android.hardware.nfc, HCE). 안테나는 가로 방향 기준 **전면 오른쪽 아래** 카드 표식 부근 — 실제 인식 범위는 태깅으로 확인 |
| PoE | 제조사 사양 IEEE 802.3at, 별도 전원 DC 12V. **구매 실기기의 PoE 옵션·실제 통전 미확인** |
| 방열 | 조회 시 CPU 약 64℃·GPU 약 65℃, 과열 경보 없음. 구조 미확인 → 72시간 송출 중 온도 기록 (PoC) |
| 키오스크 | Android 14, 기기 관리 서비스 있음. Device Owner + Lock Task로 구성 가능 (현재 미설정) |
| 설치 방향 | 카메라 위 **가로**가 기본 (Q-35) |
| adb 확인 (2026-10-27) | 제품명 `WF1589T`, 보드 `rk3576_u`, **Android 14**, 화면 **1280×800**(가로), 전면 카메라·NFC·HCE 기능 확인 |
| watchdog·정해진 시각 재부팅 | 미확인 |

PoC 시 1대를 먼저 사서 8장 기준(72시간 송출) + NFC 읽기·발급을 함께 시험합니다.

참고: NPU가 있으므로, 나중에 단말에서 얼굴 검출(얼굴이 있을 때만 AI로 보내기)을 하는 방식으로 바꿀 여지도 있습니다. 1차 범위는 아닙니다.

## 10. DB 선택: SQLite vs PostgreSQL (D-29: SQLite 확정)

| 기준 | SQLite | PostgreSQL |
|---|---|---|
| 네트워크 노출 | **없음** — 게이트 서버 프로그램만 파일을 직접 엶. 열린 포트·DB 계정이 없어 원격 공격 경로 자체가 없음 | DB 포트(5432)와 계정이 생김 → 비밀번호·접근 IP·TLS를 따로 관리해야 함 |
| 접근 제어 | OS 파일 권한 1단계 (서버 계정만 읽기·쓰기) | 사용자·역할별 권한, 행 단위 보안, 감사 로그 확장 (pgaudit) |
| 여러 서비스·개발자 동시 접근 | 약함 (쓰기는 한 번에 하나) | **강함** — 물류 서버처럼 여러 프로그램이 한 DB를 같이 쓰면 이쪽이 맞음 |
| 이중화·복제 | 없음 (파일 백업) | 복제·장애 조치 가능 |
| 운영 부담 | 없음 (파일 하나) | DB 서버 설치·업데이트·백업·모니터링 |
| 우리 부하 | 직원 200명, 출근 피크 초당 수 건 → 충분 | 충분 (여유 큼) |

**보안에서 실제로 중요한 것은 DB 종류보다 아래 항목**이며, 어느 DB를 쓰든 똑같이 필요합니다.
1. **얼굴 사진 파일**: 가장 민감한 데이터는 DB가 아니라 디스크의 사진 파일 → 서버 디스크 암호화 (BitLocker / LUKS)
2. 서버 접근: 사내망·Tailscale 안에서만, 관리자 로그인·작업 이력
3. 백업 파일 암호화와 보관 위치 제한
4. 퇴사자 얼굴 즉시 파기 (FR-A-04), 사진 보존 기간 (D-17)

**정리**: 이 시스템만 보면 SQLite가 단순하고 공격 면도 작습니다. 다만 **회사 표준이 PostgreSQL이거나, 이 DB를 다른 사내 시스템(근태·물류 등)과 같이 쓸 계획이 있으면 PostgreSQL이 맞습니다.** 바꾸는 비용은 크지 않습니다 (DB 접근이 `db.js` 한 파일, Docker로 PostgreSQL 1개 추가).
